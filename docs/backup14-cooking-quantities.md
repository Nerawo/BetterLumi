# Backup 14: actual cooking quantities

Schema 7, the `BetterLumi` database identity, and Cooking Session v2 are unchanged. No migration callback or bulk rewrite runs. Supported Backup 2–13 imports retain their previous compatibility rules; newly exported backups use version 14. Older version labels reject structural zero lines and the new reference metadata.

Recipe, meal and prepared-batch ingredient lines may have an explicit finite quantity of zero. Identity, ordering, groups, source and unit remain structural information. `lineNutrition()` contributes four numeric zeros for such lines, including when the frozen underlying nutrition has unknown fields. Positive quantities keep existing known/unknown behavior. The global nutrition multiplier and historical snapshots are not reinterpreted.

`RecipeLine.zeroQuantityReference?: {quantity: number; nutrition: Nutrition}` retains a positive reference amount and its frozen nutrition when an amount is explicitly changed to zero. It permits reliable later 0 → positive recalculation without dividing by zero or consulting mutable current data. The unit/source belong to the containing line; replacement/unit edits invalidate that association. The object accepts only its two defined keys, a finite positive amount and validated nutrition. It participates in the cooking source fingerprint. No new store/index is required.

Zero batch-source snapshots have `sourceFraction: 0`. They do not create RecipeAllocation records, source movements, source history or an `everUsed` lock. Positive allocations retain the old strict positive contract. Target batch creation and confirmed linked meals still retain the existing operation/idempotency receipt; an all-zero linked meal may have a receipt with no source movements. Deletion and preparation cancellation only return positive allocations. Structural references still require valid source identities and acyclic lineage. Invalid transactional zero allocations are rejected before restore writes.

`effectiveCookingRecipe()` produces a detached recipe at the current cooking yield, applying exact validated overrides and recalculating line nutrition from frozen references. Add Meal and Make a Batch receive this copy, never a reread of the original quantities. Existing consumed-servings/percentage controls determine the portion eaten, and existing frozen meal lines/base nutrition/allocations remain authoritative for later editing and restoration. Explicit leftover preparation retains the existing full-preparation transaction semantics. Recipe templates are untouched by these destination actions.

Update Recipe explicitly confirms a permanent template change, normalizes each effective amount by `saved yield / cooking yield`, and commits recipe quantities/nutrition and session reconciliation in one recipes/settings transaction with stale-write checks. Existing IDs and metadata remain intact; legacy missing line IDs are promoted from the session only on this explicit save. Checks remain, redundant overrides clear, and current effective amounts stay equivalent. No inventory tables participate. Built-in reference recipes remain read-only.

Integer presentation never rounds persistence. Overflow/nonfinite nutrition is rejected before committing an override-derived snapshot or template. Historical positive-only records and old session contracts are not rewritten.
