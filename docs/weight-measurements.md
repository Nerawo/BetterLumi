# Weight measurements: identity, time and compatibility

Every new measurement is inserted with a fresh UUID via weights.add. Editing uses a transaction and weights.update on the selected existing ID, preserving createdAt and checking the expected revision. Deletion retains the existing per-ID soft-delete confirmation flow. There is no date-based upsert or daily replacement.

Inspection found the existing weights store is `id,date,updatedAt,deletedAt`. The date index is already non-unique. No database migration, index replacement, table rebuild, database reset or historical-row rewrite is necessary. IndexedDB remains version 6.

New measurements have an optional-at-model-level measuredAt ISO instant with an explicit offset/UTC. The editor requires date/time for new measurements and defaults them to the current local instant. Date and time edits create a new UTC ISO instant; other edits preserve the original ISO string, including seconds/milliseconds and offset. createdAt/updatedAt remain record metadata, never measurement times. Nonexistent local times in a daylight-saving gap are rejected; new ambiguous fall-back times follow JavaScript's earlier-offset convention. Existing ambiguous-time timestamps remain exact when their visible date/time is unchanged.

Legacy rows lacking measuredAt remain unchanged, displaying Time not recorded. Their actual time cannot be reconstructed from edit/creation metadata. They continue to work; editing only weight/notes does not invent a time. Users can explicitly supply a time. Changing a legacy measurement's date requires a time as well. Legacy rows use their saved date for grouping and start-of-day positioning only for sorting/chart fallback, with stable creation/ID tie-breaking; no synthetic instant is persisted. Editing updatedAt never changes measurement order.

Known timestamps are authoritative for chronological ordering and current-local-calendar grouping, including after timezone travel. BMI, default calculator weight, Today records and the full journal reuse the same measurement ordering. The calculator no longer resolves a separate manual current-weight cache; existing legacy draft fields are retained for backup compatibility but ignored. Current weight is read-only and follows the journal, while its unit control changes the existing shared display preference only. Within each date the journal shows newest measurements first, with per-record time, weight, notes and actions. Chart points use actual measurement instants where present. The existing journal date-range filters and kg/lb preference remain available.

JSON backup format remains 9; the additive optional field round-trips in the existing record payload. Older v2–v9 backups without measuredAt remain supported. Imports validate timestamps with an explicit offset before any writes. No other backup data or migrations are removed.

Editable weight, date, time, unit and notes controls share the sans-serif UI font at 16px. Read-only weight/BMI statistics retain their existing editorial numerals. The compact shared modal retains visual-viewport resizing, safe-area padding and a scrollable body.

## Shared weight state and selected-date isolation

IndexedDB weights is the single recorded-weight source. WeightDataProvider owns one Dexie live subscription through readWeightState/resolveWeightState. Today, the journal/chart and useBmiProfile (BMI/body data/planner) consume that same state. Global latestWeight is the latest valid, non-deleted measurement by the full measuredAt instant, independent of selected date, today or updatedAt. Legacy date-only rows keep the documented ordering fallback without invented timestamps. The compatibility readBmiProfile/latestBmiWeight APIs use the same selector.

The reported mismatch came from Today selecting records no later than selectedDate and optionally borrowing an older measurement, while BMI resolved global records separately. A selected day before the latest measurement could therefore report a generic empty state despite BMI correctly showing the latest weight. Today now lists only actual measurements on selectedDate and says No weight measurements for this date when empty. Global current weight remains independent. No records are fabricated for empty days.

An additional divergence was calculator settings retaining an independent currentWeight override; these legacy values are preserved, but never override recorded weight. Current-weight display is a controlled readonly field so even a database update while it has focus updates immediately.

Known ISO timestamps are grouped using local date everywhere. Chart axis labels previously read raw saved date even though points used measuredAt; they now share measurementDate with list groups and Today. The selected calendar date is intentionally restored from route/session, not forced to today. No evidence was found that new local measurement writes used UTC date slicing. Device timezone changes on resume trigger a shared-state re-resolution via focus/pageshow/visibility events, without polling, navigation or page reload. Ambiguous legacy date-only rows remain date-only.

Regression coverage includes three same-day UI inserts, old/latest edits, soft-delete fallback, selected-empty-day isolation, reactive focused Calculator updates, kg/lb invariance, reload persistence, exact timestamps, New York/Shanghai/Auckland grouping and DST boundaries. Mobile browser coverage is Chrome touch emulation at 390/430px in Chinese/English; physical iPhone Safari/PWA needs device confirmation. Database version 6 and backup format 9 remain unchanged; no data migration, rewrite or reset is performed.

Synchronization validation: TypeScript and 310 unit tests pass. Coverage includes resume events preserving document/tab/date/draft state.
